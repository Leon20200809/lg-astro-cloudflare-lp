# LG Development Philosophy

## 0. この文書の役割

この文書は、LazyGenius流の開発判断をAIエージェントへ共有するための設計思想書である。

- `AGENTS.md`：何をしてよいか、何をしてはいけないか
- この文書：なぜその判断を選ぶのか
- `README.md`：このプロジェクトをどう使うか

AIエージェントは、原則として次の順で読む。

```text
1. AGENTS.md
2. docs/LG_DEVELOPMENT_PHILOSOPHY.md
3. README.md
4. 現在のコード
5. 今回の指令
```

現在の人間の明示指示を最優先とする。

---

## 1. LazyGeniusの基本思想

LazyGeniusは、手を抜くことを目的にしない。

目的は、無駄な作業、繰り返し、属人化、判断の迷いを減らし、人間が本質的な仕事へ集中できる状態を作ることである。

```text
Laziness
→ 同じ作業を二度やりたくない

Impatience
→ 遅い、分かりにくい、手順が多い状態を放置しない

Hubris
→ 自分たちが責任を持って保守できる品質まで仕上げる
```

LazyGenius流の「怠ける」とは、仕組みを作るために先に働くことである。

---

## 2. 最上位の判断基準

技術選択、構造変更、追加実装に迷った場合は、次の順で判断する。

```text
1. 目的を達成できるか
2. 現在の挙動を壊さないか
3. 人間が後から理解できるか
4. 責務が分かれているか
5. 検証方法が存在するか
6. 再利用できるか
7. 変更へ強いか
8. 不要な複雑さがないか
```

「新しい」「有名」「高機能」は採用理由にならない。

技術は目的を達成するための装備であり、目的そのものではない。

---

## 3. 表の目的と裏の目的

人間から「〇〇したい」という依頼を受けた場合、表面的な作業だけを見てはいけない。

```text
表の目的
→ 今回、直接達成したいこと

裏の目的
→ なぜそれをしたいのか
→ 何を楽にしたいのか
→ 何を防ぎたいのか
→ 次に何へ使いたいのか
```

例：

```text
表:
WordPressテーマへViteを入れたい

裏:
案件開始時の初期構築を消したい
CSSとJavaScriptを保守しやすくしたい
AIへ毎回同じ説明をしたくない
```

裏の目的を理解し、単発修正ではなく再利用可能な仕組みも検討する。

ただし、依頼範囲を勝手に拡大しない。必須作業と提案を分ける。

---

## 4. 事実・推定・参考・不明

AIエージェントは、知っているように振る舞わない。

- **事実**：ファイル、設定、実行結果、ログ、画面から確認できた
- **推定**：証拠はあるが確定していない
- **参考**：一般論、別案、将来の選択肢
- **不明**：現在の情報では判断できない

不明を推定へ、推定を事実へ勝手に昇格させない。

---

## 5. 最小で動かし、後から強くする

LazyGenius流は、最初から完全装備を目指さない。

```text
最小で動かす
→ 現在地を確認する
→ 一つずつ改善する
→ 検証する
→ 再利用可能な形へ整える
```

最初の実装で求めるもの：

- 動く
- 小さい
- 説明できる
- 検証できる
- 戻せる
- 次の変更を受け入れられる

将来使うかもしれない機能を、根拠なく先に追加しない。

---

## 6. 全体像から小さな一歩へ進む

実装前に全体地図を示し、一度に扱う範囲を小さくする。

```text
全体像
→ 現在地
→ 今回の一歩
→ なぜ必要か
→ 実行
→ 結果確認
→ 次の一歩
```

大きなコードを一気に出さない。

AIが自律実装する場合も、変更、コミット、検証を小さな責務単位へ分ける。

---

## 7. まず状態確認する

変更より先に状態を見る。

```text
Git
→ ブランチ
→ 未コミット変更
→ HEAD
→ remote

コード
→ 呼び出し元
→ 依存先
→ 入力
→ 出力
→ 副作用

環境
→ バージョン
→ URL
→ ポート
→ 環境変数
→ ログ
```

エラー対応：

```text
状態確認
→ 再現
→ 証拠取得
→ 原因候補
→ 最小修正
→ 再検証
```

推測から修正を始めない。

---

## 8. 一つの責務は日本語一文で説明できること

関数、クラス、ファイル、モジュールは、日本語一文で役割を説明できる大きさにする。

良い例：

```text
この関数はフォーム入力値を検証する。
このファイルはテーマのCSSとJavaScriptを読み込む。
このモジュールはハンバーガーメニューを初期化する。
```

複数の動詞が並ぶ場合は責務分離を検討する。

ただし、細分化しすぎて追跡不能にしない。

---

## 9. 指揮官と実働部隊を分ける

全体の順番を決める場所と、実際の処理を行う場所を分ける。

```text
functions.php
→ 読み込み順を決める司令塔

inc/*.php
→ 各機能を担当する実働部隊

src/main.ts
→ フロント資産の入口

src/ts/init.ts
→ UI初期化の司令塔

src/ts/components/*.ts
→ 各UIの実働部隊
```

司令塔へ重い処理を書かない。

---

## 10. 入力・処理・出力を明確にする

処理を設計する時は、次を定義する。

```text
入力
処理
出力
副作用
失敗時の挙動
```

フォーム、API、スクレイピング、CLI、WordPressフックでは特に重要である。

---

## 11. バリデーションは境界で行う

外部から入る値は信用しない。

対象例：

- フォーム入力
- URLパラメータ
- REST API
- CSV / JSON
- データベース
- 環境変数
- WordPressオプション
- 外部サイトHTML

処理内部へ渡す前に、存在、型、形式、許容値、長さ、権限を確認する。

出力時には出力先に応じてエスケープする。

バリデーションとエスケープは別の責務である。

---

## 12. エラーは隠さず、利用者へ壊れ方を見せない

悪い対応：

- Warningを画面へ垂れ流す
- 例外を握りつぶす
- `@` で隠す
- 空のcatch
- 成功したように見せる

良い対応：

```text
利用者
→ 安全で分かりやすい失敗表示

開発者
→ ログ、例外、状態、再現条件
```

---

## 13. ハードコードと設定化

すべてを設定化する必要はない。

変更可能性や事故リスクが高い値を分離する。

- URL
- ポート
- APIキー
- メールアドレス
- パス
- ドメイン
- サイト名
- 件数
- timeout
- 環境差
- 認証情報

変化しない仕様まで設定化し、理解を難しくしない。

---

## 14. 環境変数

秘密情報と環境依存値はコードへ書かない。

```text
.env
→ 実値

.env.example
→ 必要なキーと説明

コード
→ 値を利用する
```

値がない場合に、停止、既定値、機能無効化、警告のどれを選ぶか定義する。

---

## 15. 既存資産を壊さず段階的に近代化する

古いという理由だけで全面置換しない。

```text
現在の挙動を確認
→ 境界を作る
→ 新旧を共存
→ 小さく移行
→ 検証
→ 古い処理を削除
```

WordPress、Vanilla JavaScript、既存CSSは、目的を果たしている限り有効な資産である。

---

## 16. 静的検索だけで未使用と断定しない

WordPressやフロントエンドには、文字列検索に出ない呼び出しがある。

- WordPressフック
- テンプレート階層
- ショートコード
- 管理画面設定
- 動的import
- CSSクラス
- プラグイン生成HTML
- REST API
- データベース内コンテンツ

削除前に、コード検索、管理画面、ブラウザ、Network、Console、データ、プラグインを確認する。

「検索に出ない」は削除の証拠ではない。

---

## 17. UIは観測してから作る

ゼロから発明する前に、参考サイトや既存UIを観測する。

確認するもの：

- 情報の順番
- 余白
- サイズ
- 視線誘導
- PCとスマートフォンの違い
- 操作
- 状態変化
- アクセシビリティ
- なぜそのUIなのか

見た目だけでなく目的と構造を理解する。

---

## 18. WordPressの思想

WordPressはCMSとしての運用性を活かす。

```text
WordPress
→ コンテンツ管理
→ PHPテンプレート
→ 投稿・固定ページ
→ メニュー
→ 権限
→ 画像
→ 管理画面
```

WordPressが得意な処理を無理にJavaScriptへ移さない。

テーマではWordPress API、テンプレート階層、適切なenqueue、エスケープ、template parts、フックを優先する。

---

## 19. Viteの思想

ViteはWordPressを置き換えない。

```text
WordPress
→ ページを配信する

Vite
→ CSSとTypeScriptを開発・ビルドする
```

Viteの担当：

- CSS開発
- TypeScript開発
- HMR
- 本番ビルド
- manifest
- モジュール管理

開発時に確認するのはWordPress側URL。本番へdev serverを持ち込まない。

---

## 20. CSSの思想

```text
tokens
→ 設計値

base
→ 最小初期化

components
→ 再利用部品

pages
→ ページ固有

responsive
→ 画面幅対応

utilities
→ 最終調整
```

BEMとTailwindを敵対させない。

```text
BEM
→ 意味と構造

Tailwind
→ 余白、配置、サイズ、レスポンシブ

自作CSS
→ 世界観、複雑装飾、状態
```

Tailwind Preflightは、WordPress本文を壊す可能性があるため、採用理由なしに有効化しない。

---

## 21. JavaScriptとReactの思想

通常のUIはVanilla TypeScriptを優先する。

Reactは次の場合に検討する。

- 状態が複数連動する
- UI更新が頻繁
- 独立コンポーネントになる
- Vanillaでは複雑になる
- 読み込むページを限定できる

Reactを使えることと、Reactを使うべきことは別である。

---

## 22. テストと検証

コードを書いたことは成果ではない。

動作を確認し、証拠を残したことが成果である。

変更内容に応じて、構文、型、build、ブラウザ、Console、Network、レスポンシブ、ログ、Git差分を確認する。

報告するもの：

- 何を実行したか
- 成功したか
- 何を確認したか
- 何が未確認か

未実行の検証を成功と報告しない。

---

## 23. Gitの思想

Gitは保存装置ではなく、変更理由の証拠である。

良いコミット：

- 一つの目的
- 差分が理解できる
- 戻せる
- メッセージから理由が分かる
- 無関係な変更がない

変更前に状態を確認し、人間の未コミット変更を壊さない。

---

## 24. READMEとdocs

READMEは、初めて触る人が次を理解できるようにする。

- 何のプロジェクトか
- 何を解決するか
- どう動かすか
- どこを変更するか
- どう検証するか
- 困った時にどこを見るか

調査結果、作業計画、重要な設計判断は `docs/` に残す。

チャットだけを唯一の記録にしない。

---

## 25. 再利用と自動化

同じ作業を二度行ったら、三度目を消す方法を考える。

再利用候補：

- テンプレート
- 関数
- モジュール
- CLI
- シェルスクリプト
- README
- AGENTS.md
- チェックリスト
- 自動テスト
- GitHub Actions

ただし、一度しか使わないものを無理に抽象化しない。

自動化は、まず手動で入力、出力、失敗条件を理解してから行う。

---

## 26. AIエージェントの役割

AIエージェントは指示待ちのタイピング装置ではない。

- 現状を調べる
- 目的を理解する
- リスクを見つける
- より良い選択肢を提案する
- 必須と提案を分ける
- 小さく実装する
- 検証する
- 記録する

ただし、人間の目的を勝手に変更せず、作業範囲を勝手に広げない。

---

## 27. 提案の分類

```text
必須
→ 現在の目的達成に必要

推奨
→ 品質、保守性、安全性を改善

任意
→ 将来的な選択肢
```

提案には理由と費用を添える。

---

## 28. 報告形式

広い任務では、原則として次の順で報告する。

```text
結論
確認できた事実
実施したこと
変更理由
検証結果
未確認
既知の制約
次の一手
```

長い報告はMarkdownにも保存する。チャットでは判断に必要な要点を先に出す。

情報量を増やすことを、良い報告と勘違いしない。

---

## 29. 最終原則

迷った場合は次へ戻る。

```text
目的は何か
現在の事実は何か
最小の一歩は何か
何を壊す可能性があるか
どう検証するか
将来の人間が理解できるか
```

LazyGenius流の完成形は、コード量の多さではない。

```text
少ない手順
明確な責務
戻せる変更
確認できる結果
再利用できる知識
```

これらが揃った状態を、強い開発と呼ぶ。
